## Machine-readable organizations

aiaiaiai tech. builds software that can explain itself.

Every repository contains more than code. It can also contain a versioned organizational manifest describing identity, governance, engineering, portfolio, and decisions in a form both people and machines can understand.

The repository is not merely where the organization stores its work.

**The repository is the organization.**

```text
Repository  == Organization
Commits     == Decisions
Manifest    == Identity
Graph       == Company
```

Every company is a graph of people, decisions, code, and capital. Most companies keep that graph in the least machine-readable places possible: individual memory, meetings, chat threads, and documents that become stale almost immediately.

We run the inverse. Everything an organization *is* lives in a **mind**: a versioned, machine-readable manifest committed alongside the code like any other engineering artifact. The organization chart becomes a data structure. Strategy becomes diffable. History gets a hash.

> **If it is not in the manifest, it is not real. If it is in the manifest, a model can reason about it.**

## Principles

- **Machine-readable by default.** Decisions, scope, and structure live in versioned manifests rather than individual memory.
- **Local-first inference.** Explanations are generated by a local model over WebGPU at the moment they are requested.
- **Provider-agnostic cores.** Domain logic should not depend on a particular vendor, interface, deployment platform, or delivery channel.
- **Structure over policy.** Important rules belong in schemas, invariants, and automation—not documents that merely ask people to remember them.
- **Heavy lifting stays boring.** Indexing, caching, and vector search run on commodity infrastructure. The differentiated layer is the last inch that runs on the user's machine.
- **Ship the specification.** Open questions remain explicitly open. We do not ship confidence we have not earned.
- **Public systems should be inspectable.** Architecture, status, ownership, and limitations should be visible in the repositories that implement them.
